## 二、工程补齐（目标 1）

### 2.1 依赖补齐 —— `package.json`（修改）

原 `package.json` 仅声明 26 个依赖，但源码实际 `import` 了约 **55 个第三方包**，缺失约 30 个，直接运行必然报模块找不到。

**补齐的缺失依赖**（均按源码中的实际 import 推断，未新增任何源码未使用的库）：

| 类别 | 补充的包 |
| --- | --- |
| Radix UI（shadcn 组件依赖） | `@radix-ui/react-accordion`、`-alert-dialog`、`-aspect-ratio`、`-checkbox`、`-collapsible`、`-context-menu`、`-hover-card`、`-menubar`、`-navigation-menu`、`-popover`、`-progress`、`-radio-group`、`-scroll-area`、`-slider`、`-switch`、`-toggle`、`-toggle-group`、`-tooltip` |
| UI 功能库 | `cmdk`、`vaul`、`input-otp`、`next-themes`、`qrcode`、`react-day-picker`、`react-dropzone`、`react-helmet-async`、`react-resizable-panels`、`recharts`、`video-react` |
| 构建 / 测试 | `vite-plugin-svgr`、`vitest`、`jsdom`、`@testing-library/react`、`@testing-library/dom`、`@testing-library/jest-dom`、`@types/qrcode` |

同时新增脚本：`dev:cloud`（云端模式）、`typecheck`、`test`、`build:mock`。

**为什么**：不补齐则 `pnpm dev` 直接因模块解析失败而无法启动。

### 2.2 pnpm 构建脚本放行 —— `pnpm-workspace.yaml`（修改）

```yaml
allowBuilds:
  esbuild: true
```

**为什么**：pnpm 12 默认拦截依赖的 postinstall 脚本，导致 esbuild 二进制未下载、Vite 无法启动（报 `ERR_PNPM_IGNORED_BUILDS`）。

### 2.3 删除秒哒导出残留的编译产物（删除）

删除 `vite.config.js`、`vite.config.d.ts`、`tsconfig.tsbuildinfo`、`tsconfig.node.tsbuildinfo`。

**为什么**：这是**关键的隐藏坑**。Vite 解析配置时 `.js` 优先于 `.ts`，残留的 `vite.config.js` 会让 `vite.config.ts` 的修改完全失效（表现为改了配置却毫无效果）。同理 `.tsbuildinfo` 会让 `tsc -b` 跳过重新检查。

### 2.4 散落文件核查 —— 未改动

秒哒根目录的 `HomePage.tsx`、`ArtisanDetailPage.tsx` 经哈希比对与 `src/pages/` 下同名文件**完全一致**，属重复下载，无需归位（移动反而会造成无意义改动）。

## 三、演示模式实现（目标 3）

> 由于源码不含 Supabase 凭据，云端真库不可用，改为实现**默认开启的演示模式**。

### 3.1 新增 `src/db/supabase.mock.ts`（新增）

一个**内存版 Supabase 客户端**，实现了业务代码实际用到的全部 API：

- **PostgREST 查询构造器**：`from().select()/insert()/update()/delete()`，链式 `.eq() .or() .ilike() .order() .limit() .maybeSingle() .single()`，含 `count` 统计
- **Auth**：`getSession / onAuthStateChange / signInWithPassword / signUp / signOut`
- **Storage**：`upload / getPublicUrl / remove`（用 `URL.createObjectURL` 实现）
- **Edge Function**：`functions.invoke()`（返回失败，触发 AI 工坊降级）
- **模拟云端 RLS**：普通用户只能读写自己的预约/订单/AI 纹样，管理员可见全部，未登录不可见
- 数据持久化到 `localStorage`（刷新不丢），并提供 `__wenzangMock.reset()` 重置

### 3.2 新增 `src/db/mockData.ts`（新增）

演示种子数据。**字段结构与 `supabase/migrations/00001` 的建表语句完全一致**，其中 7 条纹样、3 位守艺人、3 个体验项目、3 件商品直接取自 `00002_seed_wenzang_data.sql`，其余按同一风格扩写：

- **15 条纹样**（蜡染 6 / 扎染 5 / 苗绣 4）
- 3 位守艺人、3 个体验项目、3 件文创商品
- 示例预约 3 条（分属两位用户，便于演示管理员可见全部）、订单 1 条
- 内置账号：管理员 `admin@miaoda.com`、普通用户 `demo@miaoda.com` 等

### 3.3 `vite.config.ts`（修改）—— 演示模式切换机制

新增按 `mode` / `VITE_USE_MOCK` 决定是否启用别名：

```ts
const useMock = mode === "cloud" ? false : mode === "mock" || env.VITE_USE_MOCK === "1";
// ...
...(useMock ? [{ find: /^@\/db\/supabase$/, replacement: ".../supabase.mock.ts" }] : []),
```

**为什么这样设计**：这是本次改造的核心决策。通过**构建期路径别名**替换数据源，而不是在每个页面里写 `if (isMock)` 分支，带来三个好处：

1. `api.ts`、`AuthContext.tsx`、全部页面组件**一行都不用改**，云端调用语义原样保留；
2. 视觉与组件结构零风险；
3. 源码证据价值完整——评委看到的就是真实的 Supabase 调用代码。

**注意 `--mode cloud` 强制关闭演示模式**：Vite 的 `.env.local` 在**所有** mode 下都会被加载，若不做这层覆盖，`.env.local` 里的 `VITE_USE_MOCK=1` 会导致 `pnpm dev:cloud` 也走演示模式，与"连云端"的预期相反。

### 3.4 `src/db/supabase.ts`（修改）—— 模式标识

新增导出一行：

```ts
export const isMockMode = false; // 演示模式下本文件被别名替换，mock 实现中为 true
```

**为什么**：判断"当前是否演示模式"最可靠的方式，是**问数据源本身**，而不是各处重复判断环境变量。`src/lib/role.ts` 通过 `import { isMockMode } from "@/db/supabase"` 获取该标识，从而在两种模式下自动选择"按邮箱判定管理员"或"读 profiles.role"，且不会与环境变量判断不一致。

### 3.5 新增 `.env.local` / `.env.example` / `.gitignore`（新增）

`VITE_USE_MOCK=1` 默认开启演示模式，并附云端模式的填写说明；`.gitignore` 排除 `node_modules`、`dist`、`.env.local` 等。

## 十一、P0-1：AI 工坊 · 程序化纹样生成

**背景**：原降级方案只出文字不出图，答辩演示时核心功能"不出图"是最大软肋。

### 11.1 新增 `src/lib/patternArt.ts`

纯前端程序化纹样生成器，**原生 SVG 实现，零外部依赖**（未引入 p5 / paper.js 等）。

| 能力 | 说明 |
| --- | --- |
| 5 组矢量基元 | `butterfly` 蝴蝶（对称双翼+卷草触须）、`drum` 铜鼓（同心圆+太阳芒纹+翔鹭纹）、`fish` 鱼纹（鱼形+涡妥水波）、`flower` 团花（八瓣+石榴花心）、`geo` 几何（菱格+点阵+冰裂纹） |
| 关键词映射 | 蝴蝶/妈妈/凤→butterfly；铜鼓/太阳/鼓→drum；鱼/水/涡→fish；花/石榴/团花→flower；几何/点/格/冰裂→geo |
| 叠层规则 | 命中多个关键词取前两个叠层；命中单个时补搭配基元（如蝴蝶+团花）；无命中时按类别默认（蜡染→drum、扎染→geo、苗绣→butterfly） |
| 三种布局 | 中心对称 / 轴对称 / 四方连续，随机选取 |
| 确定性随机 | FNV-1a 哈希 + mulberry32，种子 = hash(`主题词\|类别\|变体号`)，**同参数必然复现** |
| 受约束配色 | 主色恒为 `hsl(218,51%,37%)`，其余为同色相明度衍生；米白底 `hsl(40,30%,96%)`；朱砂 `hsl(8,72%,45%)` 仅作点缀，代码级约束 **≤5% 面积**（`accentRatio` 可断言） |
| 导出 | `svgToDataUrl()` 供 `<img>` 直接显示；`rasterizeSvg()` 光栅化为 PNG 供上传保存 |

**为什么单独建文件**：`patternGen.ts` 原本只负责"命名与寓意"这一件事；图形生成是独立职责，放进新文件避免其膨胀、也更易单测。同时通过 `patternGen.ts` **统一再导出**，保持"生成入口在 patternGen"的对外约定不变。

### 11.2 `src/lib/patternGen.ts`（修改）

在文件末尾统一再导出 `patternArt.ts` 的能力（`generatePatternArt`、`resolveMotifs`、`hashString`、`Rng`、`buildPalette`、`rasterizeSvg` 及类型）。原有 `generateNameAndMeaning`、`buildPrompt` **逻辑未动**。

### 11.3 `src/pages/WorkshopPage.tsx`（修改）

**三级降级链**（云端恢复后无需改代码）：

```
① 云端 Edge Function 生图  → 成功则展示云端图
        ↓ 失败（无额度/断网/未配置）
② 本地程序化生成（SVG，即时出图）
        ↓ 异常
③ 提示错误（不白屏）
```

- 结果卡图案区：优先显示云端图，否则显示本地生成的 SVG
- 结果卡元信息新增：**「算法生成 · 种子XXXX」**、基元名称、布局名称
- 顶部新增小标签 **「本地程序化生成模式」**（诚实标注，答辩可讲）
- 「保存到我的纹样」：云端图直接上传；本地图先 `rasterizeSvg()` 转 PNG 再上传
- 「重新生成」按钮递增变体号产生新变体；首次「生成纹样」保持当前变体号，因此同主题词重复生成结果一致

**视觉红线**：仅替换结果卡内的图案区与元信息，页面布局、卡片结构、靛蓝体系均未改动。

### 11.4 `src/db/supabase.mock.ts`（修改）—— 修复对象存储缺陷

> 该缺陷由 `scripts/verify-save-chain.mjs` 实测暴露（保存后跳转再读，图片 `naturalWidth` 为 0），非推测。

## 十二、P0-1 返工：关键词收窄为双字词

**问题**：初版按规格把「点」「格」「花」「鱼」等**单字**作为关键词，导致输入描述性语句时会误命中基元
（如"随便写**点**什么"被判为几何基元）。

**改动**：`src/lib/patternArt.ts` 的 `KEYWORD_MAP` 全部改为**双字及以上**：

| 基元 | 收窄后的关键词 |
| --- | --- |
| butterfly | 蝴蝶、妈妈、凤凰、百鸟、飞鸟、蝴蝶妈妈 |
| drum | 铜鼓、太阳、鼓纹、光芒、星辰、鼓面 |
| fish | 鱼纹、游鱼、水波、涡妥、波浪、漩涡、双鱼 |
| flower | 团花、石榴、花瓣、莲花、花卉、八瓣、花纹 |
| geo | 几何、点阵、方格、冰裂、菱格、方胜、网格、菱形 |

**测试同步**：新增用例「描述性语句不会因单字误命中基元」，覆盖
"随便写点什么""这个格子不错""花钱买不到""我想做一条鱼""你好世界"五种输入，
断言均回落到类别默认基元；并新增「双字关键词按规格生效」用例。

> 注：本次返工改变了种子哈希的输入（关键词表参与基元解析），因此部分主题词的生成结果与 P0-1 初版不同，属预期。

## 十六、P1：商品「关联守艺人」改为下拉联动 artisan_id

**背景**：P0-2 交付时，商品管理的「关联守艺人」是一个纯文本输入框（`artisan_name`）。
名字可以随便写，于是前台拿不到 `artisan_id`，「出自 · 某某」永远只是一个字符串，
点不进守艺人档案；同名/错字/守艺人改名都会让商品与档案对不上。本次把它改为**下拉选择 + id 联动**。

### 16.1 新增 `src/lib/productLink.ts` —— 关联计算的三个纯函数

表单只产出 `artisan_id`，`artisan_name` 一律由守艺人列表派生，两列不可能各说各话。

| 函数 | 职责 |
| --- | --- |
| `resolveArtisanLink(id, artisans, fallbackName?)` | 下拉值 → 待写入的 `{artisan_id, artisan_name}`；空值即"未关联"（两列一并清空）；**未知 id 时保留原有名字**，不静默丢数据 |
| `backfillArtisanLinks(rows, artisans)` | 老数据兼容：只有 `artisan_name` 的行按名字反查补齐 id（**查不到保持 null，不报错**）；反向也补（有 id 缺名字时回填名字） |
| `keepLiveArtisanLinks(rows, liveIds)` | 前台读取校验：`artisan_id` 必须指向一位**在架**守艺人，否则清空关联 → 自动回落为纯文本 |

行类型统一收敛到 `ArtisanLink`（两列**全部可选**），因此数据层那些"老到两列都缺"的行也能安全传入，
不会在运行时抛错——这是"字段可选绝不报错"红线的落地方式。

### 16.2 `src/db/supabase.mock.ts`（修改）—— 载入时一次性修复历史数据

新增 `migrateDb()`：演示库从 `localStorage` 载入后跑一次 `backfillArtisanLinks`。
老版本浏览器里存的商品只有 `artisan_name`，刷新一次即补齐 id，前台跳转立刻可用。
`products` 表的写入路径本就是整行透传，`artisan_id` 原样保留，无需额外改动。

### 16.3 `src/lib/api.ts`（修改）—— 读取层分工：前台断链、后台回显

| 入口 | 行为 | 为什么 |
| --- | --- | --- |
| `fetchProducts()` / `fetchProductById()` | 经 `keepLiveArtisanLinks` 过滤，无效或已归档的 id **清空为 null** | 透传坏 id 会让前台渲染出「点开即 404」的死链；清空后前台无需任何判断即回落纯文本 |
| `fetchAllProductsAdmin()` | 对只有名字的老数据跑 `backfillArtisanLinks`，**只补副本、不写回数据层** | 后台下拉要能回显；但"读一次列表就改了数据"不可接受，落库交给管理员保存那一刻 |
| 守艺人列表读取失败 | `.catch` 后按空集处理，链接一律不渲染 | 宁可不给链接，也不给坏链接 |

`ProductInput` / `Product` 类型早已含 `artisan_id: string | null`，本次**未改类型**。

### 16.4 `src/pages/AdminDashboardPage.tsx`（修改）—— 下拉与提交派生

- `PRODUCT_FIELDS` 中「关联守艺人」由 `{ key: "artisan_name", type: "text" }` 改为
  `{ key: "artisan_id", type: "select", allowEmpty: true, placeholder: "暂不关联" }`；
- 选项按 `patternFields` 的同一套 `useMemo` 模式生成：来自已加载的 `artisans`、
  **排除 `status === "archived"`**，`value` 为 `artisan.id`，显示文本为 `artisan.name`；
- 提交链路 `createProductLinked` / `updateProductLinked` 用 `resolveArtisanLink` 派生 `artisan_name`
  一并写入；编辑态传入原名字作为 fallback，未知 id 不会被洗成空。

`EntityManager` 侧只补了一个通用能力：`FieldDef.allowEmpty`——
带它的 `select` 新建时**不默认选中第一项**而是留空（显示 placeholder）。
因为「类别」「擅长工艺」都是必填、天然取第一项即可，而「关联守艺人」是可选字段，
若默认关联第一位守艺人就会凭空造出错误关联。`select` 的 `optionLabels`（value→显示名）P0-3 已具备，
本次直接复用，未新增控件类型。

### 16.5 前台展示（不改布局与视觉）

| 文件 | 改动 |
| --- | --- |
| `src/pages/ProductDetailPage.tsx` | 「出自 · {artisan_name}」在 `artisan_id` 有效时渲染为 `<Link to={/artisans/:id}>`，否则保持纯文本 |
| `src/pages/ShopPage.tsx` | 同上，但**用点击跳转而非嵌套 `<Link>`** |

> **为什么商城卡片不用 `<Link>`**：卡片整体已经是一个 `<Link>`（`/shop/:id`），
> 而 HTML 规范不允许 `<a>` 嵌套 `<a>`（解析器遇到内层 `<a>` 会提前闭合外层；

> 验收脚本对这一点做了显式断言（`hasNestedAnchor === false`）。

### 17.1 任务包 2（最高优先级）：无法注册与登录

**复现**（`scripts/verify-auth.mjs`，全新浏览器 / 等效隐身模式）：
注册 → 自动登录 → 刷新保持登录 → 退出 → **重新登录失败**，停在 `/login`；
密码错误时 toast 只写「操作失败」，看不出是密码错还是功能坏。

**三条根因**：

| # | 根因 | 证据 |
| --- | --- | --- |
| ① | 注册账号只 `MOCK_USERS.push()` 进内存常量，**没有落盘**。刷新后模块重新求值、数组回到种子状态，刚注册的账号凭空消失 | 数据层探针：同一次会话内 `signUp` 后 `signIn` 成功，重载后同一凭据 `Invalid login credentials` |
| ② | `signUp` 不在 `profiles` 表建档（云端有"注册自动建档"触发器，演示层缺失），运营看板「注册用户数」永远不含新注册用户 | 注册后 `profiles` 仍为 3 条，看板 userCount 恒为 3 |
| ③ | 认证失败返回的是**普通对象** `{ message }` 而非 `Error` 实例，登录页 `err instanceof Error ? err.message : "操作失败"` 判不中，中文映射（`Invalid login → 用户名或密码错误`）永远走不到 | 浏览器实测 toast 文本为「操作失败」 |

**修复**：

- `src/db/supabase.mock.ts`
  - 新增账号表 `accounts`：种子账号 + 本地注册账号，**持久化到 `localStorage` 键 `wenzang.mock.users.v1`**；
    种子账号始终以代码为准（内置账号改密/新增可随版本生效），本地注册账号叠加在后面，
    因此**用户无法通过注册冒领 admin**；
  - `signUp` 落盘账号 + 同步 `ensureProfile()` 建 `profiles` 档案 + `persist()`；
  - `signInWithPassword` 也调用 `ensureProfile()`，兼容"账号在、档案被重置掉"的情况；
  - 认证错误改为返回真正的 `Error` 实例（与云端 `supabase-js` 行为一致）；
  - `mockRole()` 由"只认内置管理员邮箱"扩展为"邮箱命中种子管理员或账号 role=admin"。
- `src/pages/LoginPage.tsx`：新增并导出 `authErrorMessage()`，把英文错误统一翻成中文
  （`Invalid login credentials → 用户名或密码错误`、`User already registered → 该用户名已被注册`），
  取不到 message 时兜底「操作失败，请稍后重试」——**任何失败都有可读提示，不静默**。

**账号数据与演示数据分离**：账号存在独立键里，所以第十七 5 节的「重置演示数据」不会把注册用户一起清掉。

### 17.2 任务包 3：相关纹样出现重复条目

### 17.3 任务包 1：路由切换后滚动位置不复位

**滚动容器确认**（脚本 `verify-scroll.mjs` 检查点 0a）：
`document.documentElement.scrollHeight > innerHeight`、`<main>` 的 `overflow-y: visible`、
页面内**不存在**任何 `overflow:auto/scroll` 的内层滚动容器 ⇒ 实际滚动的是 **window**。

**根因**：SPA 客户端跳转不触发浏览器自带的滚动复位，而路由层从未做过复位处理，
所以从长列表深处进入新页面时视口停在原位。线上旧版实测残留 `scrollY=1010`、`186`。

**修复**：新增 `src/components/common/ScrollToTop.tsx`，挂在 `App.tsx` 的 `BrowserRouter` 内、`Routes` 外，
对所有页面生效。要点：

- 复位条件取 **`pathname + search`**：后台 `?tab=products` 与个人中心 `?tab=orders` 都是整块内容替换，
  只按 pathname 会漏掉这两类切换（实测切 tab 前 `scrollY=1013`，复位后 0）；
- **首次挂载不复位**，把滚动恢复留给浏览器，前进 / 后退不报错也不强行回顶；
- 用 `window.scrollTo(0, 0)`，不引入任何依赖。

### 18.2 任务包 C：返回列表时恢复原浏览位置

**根因**：上一版 `ScrollToTop` 对**所有**导航一律 `scrollTo(0, 0)`，把 PUSH 和 POP 混为一谈；
而详情页的「返回纹样图库」是 `<Link to="/patterns">`，属于 **PUSH** 而非 POP——
所以返回必然被顶到顶部，长列表的浏览位置丢失。浏览器原生的滚动恢复在客户端路由下不生效
（历史条目换了，但页面从没真正卸载重载）。

**修复**：`ScrollToTop.tsx` 升级为 **`ScrollManager.tsx`**（旧文件删除）：

- 用 `useNavigationType()` 区分方向：**PUSH / REPLACE → 回顶**（保留既有验收行为），
  **POP → 按 `location.key` 恢复**；
- 每个 `location.key` 离开时的 `scrollY` 记进 `sessionStorage`（`wenzang.scroll.v1`，容量 50 条 FIFO 淘汰）；
- 恢复用 `requestAnimationFrame` **重试至多 30 帧**——详情页的档案区块和图片是异步撑高的，
  一次 `scrollTo` 会被后续布局顶掉；
- 显式设 `history.scrollRestoration = "manual"`，避免与浏览器自带恢复互相覆盖；
- 首次挂载不复位，前进 / 后退不报错。

| `src/components/common/ScrollManager.tsx` | **新增**，替换 `ScrollToTop.tsx`（已删除） |
| `src/App.tsx` | 挂载点不变，组件改名 |

## 七、顺带修复的两个既有缺陷

改造过程中实测发现的**原有 Bug**（非本次引入），一并修复：

### 7.1 刷新页面丢失登录态导致误跳转

**文件**：`src/pages/ProfilePage.tsx`、`src/pages/LoginPage.tsx`

- **现象**：直接访问或刷新 `/profile?tab=bookings`、`/profile?tab=admin` 时，页面会先被重定向到 `/login`，登录后又跳回默认的「我的纹样」页，**丢失 `tab` 参数**。
- **原因**：`AuthContext` 恢复会话是异步的，初始 `session` 为 `null`。`ProfilePage` 的 `useEffect` 未等待 `loading` 结束就判定「未登录」并跳转；`LoginPage` 更是在**渲染过程中**直接调用 `navigate()`。
- **修复**：`ProfilePage` 等待 `authLoading` 结束后再判断，并保留 `tab` 参数；`LoginPage` 改为在 `useEffect` 中跳转；两者在鉴权未确定时显示加载占位而非空白。

**为什么重要**：这是**答辩现场真实会踩的坑**——演示时若刷新页面或直接输入带 `?tab=admin` 的地址，管理员入口会「看起来不存在」。

### 7.2 图标在断网时无法显示

**文件**：`index.html`

favicon 原指向外部 CDN，改为本地 `public/images/favicon.ico`。
